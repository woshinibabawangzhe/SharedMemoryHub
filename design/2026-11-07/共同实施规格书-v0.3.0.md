### 本版实施契约

1. 看板正文始终作为纯文本通过 DOM `textContent` 渲染。外部同源脚本配合 CSP；记忆字段不参与 HTML、事件处理器或脚本插值。看板提供编辑正文/适用元数据、锁定、暂停、软删、Undo、历史对比、指定版本恢复、提案采纳/拒绝/手动合并。
2. 首次管理员初始化仅由终端交互输入，经 stdin 进入初始化程序，仅存 scrypt 加盐哈希。没有固定默认口令；已有认证保持。原 `reset_admin_passcode.ps1` 名称保留兼容，但只允许初始化缺失认证，不覆盖原配置。所有管理员写操作同时验证会话、CSRF 和配置的准确 Origin，缺失 Origin 也拒绝。
3. 模块导入不创建数据库、认证或向量客户端。启动生命周期先取得实例锁，再核认证、Schema、墓碑与恢复。旧库返回 `migration_required`，不自动改库。`scripts/migrate_schema.py --runtime <运行根>` 是唯一显式离线迁移入口：先检查墓碑和水位，备份 SQLite，事务增加清除进度并置 `PRAGMA user_version=300`；本轮仅对合成实例验证。
4. Purge 必须提供当前 `expected_revision` 和完全匹配的 `confirm_purge="PURGE <memory_id> r<expected_revision>"`。先 fsync 外部墓碑，再提交逻辑删除。SQLite/向量/受管理导出/整理分别持久记录进度；未全部完成返回 HTTP 202、`purge_pending`，核验完成才返回 `purged`。后台、启动和备份恢复继续重试未完成清除。只对真正不存在的新数据库生成创世墓碑；已有库缺失、截断或损坏墓碑拒绝上线。
5. 向量写入、清除和重建共用串行边界；写后核修订、世代、状态与条件更新行数，失效任务补偿删除，删除失败保留持久待办。清除枚举本实例集合前缀的全部世代，避免恢复较旧 SQLite 后遗漏新世代。SQLite 为最终读取权威，已提交清除的记忆立即停止有效读取。
6. 合格项目内的明确偏好可以自动成为 `confirmed`；模型推断保留为 `hypothesis`。全局范围（`global` 为兼容拼写，推荐 `user_global`）与规则候选创建为暂停记录并产生提案。更新先合并已有字段，省略字段保留；handoff 无论省略还是显式空 TTL 都维持 7 天默认、30 天上限。人工编辑、Undo、Restore、裁决共用校验与完整内容/适用范围快照，修订号冲突拒绝覆盖；采纳过时提案须先手动合并。
7. 同步数据库、推理、重建和整理在工作线程执行，ASGI 事件循环保持响应。仍是单进程、单串行索引 Worker、模型互斥。唯一运行向量后端是 Docker Qdrant REST，不自动使用嵌入式替代；离线明确 `keyword_only`。实际模型适配使用原生 Transformers + PyTorch，不安装 Mem0 或额外的 sentence-transformers 包。
8. `.venv-0.3.0` 不继承系统包，旧 `.venv` 保留。`requirements.lock` 由实际下载的 Windows cp313 wheel 生成 SHA256 并以 `--require-hashes` 安装；官方 `torch==2.11.0+cu128` 构建须核验官方哈希。镜像固定 `qdrant/qdrant@sha256:318c11b72aaab96b36e9662ad244de3cabd0653a1b942d4e8191f18296c81af0`（v1.13.4）。默认 CUDA 不可用时明确报错，CPU 回退必须显式选择并单独验收。

## 1. 系统工程定位、无 Mem0 原生技术栈与混合部署拓扑

### 1.1 为什么去掉 `mem0ai` 中间商包（与前期研究的收敛说明）

1. **前期核验事实**：在 `Codex-技术研究与对接设计-v0.1.0.md`（§4）与 `Antigravity-产品与管理看板研究-v0.1.0.md`（§2）中，双方通过源码核验查明：`mem0ai==2.2.1` 的 `Memory` 主类无条件初始化 OpenAI LLM、公共 `add(infer=False)` 生成随机 UUID 导致崩溃重试产生重复幽灵点、`SQLiteManager` 缺乏完整快照与恢复契约、默认向 `~/.mem0` 写文件并开启 PostHog 遥测，且 `HuggingFaceEmbedding` 忽略了 `memory_action` 参数；而 `mem0ai/openmemory` 的旧自托管 Web/MCP 快照（`b0bfce4b`）已归档。
2. **收敛决策**：如果绕过 `Memory` 主类而仅调用 Mem0 内层的 `HuggingFaceEmbedding` 与 `Qdrant` 包装，实际只复用了不到百行薄转接代码，却仍需承担屏蔽 Mem0 默认遥测、默认目录与版本升级破坏内部签名的维护包袱。因此，**本系统直接采用官方原生组件组合，不再安装 `mem0ai` 包**。

### 1.2 最终采用的四层原生技术栈与混合部署拓扑

```text
[调用层] Antigravity / Codex 当前主模型 (第1步：按需检索 + 提炼可读记忆卡片)

## 2. 三步分工、分级准入与自动修改边界（修订 P0-1 & P0-2）

### 2.1 三步分工契约

1. **第 1 步（当前对话主模型提炼）**：用户在 Antigravity 或 Codex 会话中交流时，由当前主模型按 §5.2 触发规则提炼结构化记忆卡片，先调 `memory_precheck` 查重，再调 `memory_write` 提交（中心后台零生成式 LLM 开销）。
2. **第 2 步（本地 `0.6B` 向量编码）**：单串行 Worker 从 SQLite 认领待索引任务，调用本机 `Qwen3-Embedding-0.6B` 生成 1024 维归一化向量。
3. **第 3 步（统一记忆服务持久化与治理）**：SQLite 单事务负责原文、版本号、防重、FTS5 子串索引与待办任务落盘；Qdrant 负责保存确定性 UUIDv5 向量点供语义检索。

### 2.2 确定性准入守卫与来源可信度分级规则（`AdmissionGuard`，修订 P0-1）

由于中心不运行后台 LLM，网关在 `memory_write` 入库前执行以下确定性代码级守卫与可信度核验：

#### (1) 基础结构、敏感凭据与越权指令拦截（不通过直接返回 `422 Unprocessable Entity`）
1. **长度与结构守卫**：`title` 非空且 `<= 120` 字符；`content` 非空且 `<= 4000` 字符（禁止将整篇文档或原始长对话全文直接塞入单条记忆）；`topic_key` 符合 `^[a-z0-9_.-]{3,80}$`。
2. **敏感凭据正则拦截（`SecretPatternGuard`）**：扫描 `title`、`content` 与 `source_json`，若匹配常见密钥/凭据特征（如 `sk-[A-Za-z0-9]{20,}`、`ghp_[A-Za-z0-9]{20,}`、`AKIA[0-9A-Z]{16}`、`-----BEGIN [A-Z ]+ PRIVATE KEY-----`、`Bearer\s+[A-Za-z0-9._-]{20,}`、以及形如 `API_KEY=...` / `PASSWORD=...` / `TOKEN=...` 的明文赋值），直接拒绝并返回 `error_code = "sensitive_credential_rejected"`。
3. **越权指令拦截（`PrivilegeEscalationGuard`）**：扫描是否包含试图篡改宿主安全与审批边界的指令模式（如 `"ignore previous instructions"`、`"忽略审批"`、`"自动开启 auto_continue"`、`"允许读取 .env"`、`"绕过权限"`），匹配时直接拒绝并返回 `error_code = "policy_violation_rejected"`。

#### (2) 四类来源枚举（`source_type`）、真实磁盘证据核验与降级规则（防止“字符串非空即当真”）
客户端提交的 `source.origin_type`（对应落库字段 `source_type`）必须属于以下枚举，且服务端对**可做磁盘实体核验的证据**与**无法做语义真伪核验的对话摘录**执行严格区分与自动降级，**绝不将 `evidence_ref` 非空字符串直接等同于已核验事实**：

| `source_type` 枚举 | 含义与适用场景 | 必填 `source_json` 证据字段与服务端真伪核验动作 | 核验失败或无法验证时的强制降级规则 |
| :--- | :--- | :--- | :--- |
| **`project_fact`** | 项目内可核查的客观配置、代码结构或架构契约 | 必填 `evidence_path`（项目内相对文件路径）+ `evidence_ref`（配置键/锚点说明），可选完整 `evidence_sha256`（不接受前缀）或 `evidence_snippet`。<br>**服务端核验**：拼接当前 `bound_workspace_path / evidence_path`，调用 `os.path.isfile` 核验该文件在磁盘**真实存在且可读**（若带哈希/片段则核验一致），通过则标记 `verification_status='disk_verified'`。 | 若文件不存在、路径越界或哈希/片段不匹配：**服务端拒绝授予 `confirmed`，自动降级为 `confidence = 'hypothesis'`**（返回 `downgrade_reason = "unverified_project_file"`）。 |
| **`verified_receipt`** | 经实际命令执行、测试通过或收据验证的排障经验 | 必填 `evidence_path`（指向 `E:/AI运行区/...`、`E:/Harness运行区/...` 或工作区内真实存在的测试结果/收据文件）+ `evidence_ref`（退出码或验证结论），可选 `evidence_sha256`。<br>**服务端核验**：核验 `evidence_path` 在磁盘真实存在非空且哈希匹配，通过则标记 `verification_status='disk_verified'`。 | 若收据文件不存在或哈希不匹配：**服务端自动降级为 `confidence = 'hypothesis'`**（返回 `downgrade_reason = "missing_or_mismatched_receipt"`），严禁仅凭口头声称“测试通过”进入有效经验库。 |
| **`user_explicit`** | 用户在对话中明确下达或拍板确认的偏好/决定 | 必填 `session_id` + `evidence_ref`（用户轮次标识或原话摘录，`>= 4` 字符）。<br>**服务端核验边界声明**：对于 Antigravity 可核查本机 `sessions/<session_id>/context.json` 存在；但因网关不运行 LLM，**无法在代码层语义核验 AI 摘录是否忠实于用户原意**，故统一标记 `verification_status='unverified_excerpt'`。 | • 若缺 `session_id` 或 `evidence_ref`：直接降级为 `confidence='hypothesis'`；<br>• **高影响动作保护**：凡涉及 `scope='user_global'`、`kind='rule_candidate'` 或跨会话修改/删除既有已生效记忆，即使填了 `user_explicit` 也**一律不直接生效**，强制转入 `paused` / `conflict_proposals` 待人工批准；<br>• 低风险已绑项目内新建允许 `confirmed` 入库，但在看板顶部“最近自动新增（待审阅）”横幅高亮并提供一键 **Undo**。 |
| **`model_inference`** | 主模型根据上下文自行推断、归纳或猜测的结论 | `session_id`（可选附推理说明） | **无论请求体填写什么，服务端一律强制覆写为 `confidence = 'hypothesis'`**，严禁模型猜测混入常规检索。 |
| **`admin_manual`** | 用户在管理看板 `/ui` 手工新建或编辑 | 服务端自动填充 `actor_role='user_admin'`, `verification_status='admin_confirmed'` | 仅限 `user_admin` 通道使用，`agent_client` 伪造此类型直接返回 `403`。 |

#### (3) 五类记忆（`kind`）的差异化准入、生命周期与防自动覆盖矩阵（保留低风险自动化，保护重要记忆）

| 记忆类别 (`kind`) | 允许 `agent_client` 直接新建为 `active` 的条件 | 强制过期 (`expires_at`) 规则 | `agent_client` 后续修改 (`update`) / 删除 (`soft_delete`) 规则 |
| :--- | :--- | :--- | :--- |
| **`preference`**<br>（长期/项目偏好） | `scope` 为已绑定 `project` 或 `agent_private`，且 `source_type == 'user_explicit'` | 默认 `NULL`（长期有效） | • 若为**同端同会话新建自纠**（`created_by_actor_id == actor_id AND created_in_session_id == session_id AND locked == 0`），允许直接更新/软删；<br>• **跨会话或跨端修改/删除已生效偏好**：一律拦截转为 `conflict_proposals`（`update_proposal` / `delete_proposal`），原记录保持 `active` 待人工批准。 |
| **`context`**<br>（项目技术决策/背景） | `scope == 'project'`（已绑定），且 `source_type IN ('user_explicit', 'project_fact')` | 默认 `NULL`（随项目有效） | 同上：仅允许同端同会话内自纠；对既有跨会话项目决策的修改/删除一律转为提案待人工批准。 |
| **`experience`**<br>（已验证排障经验） | `scope` 为已绑定 `project` 或 `agent_private`，且 `source_type IN ('verified_receipt', 'user_explicit')` | 默认 `NULL`（若缺验证证据则自动降为 `hypothesis`） | 同上：已生效验证经验禁止被后续会话 AI 直接覆盖或删除，修改请求一律转为提案。 |
| **`handoff`**<br>（临时任务/交接状态） | `scope` 为已绑定 `project` 或 `agent_private` | **强制短期 TTL**：若未填 `expires_at` 自动补填 `now + 7d`（最长不超 `now + 30d`） | **允许低风险自动流转**：在已绑定同项目且 `locked == 0` 下，允许 `agent_client` 直接 `update` 或 `soft_delete` 以更新短期任务进度。 |
| **`rule_candidate`**<br>（规则/全局规范候选） | **禁止直接 `active`**：初始强制置为 `state = 'paused'` 并生成 `conflict_proposals(proposal_type='rule_candidate')` | 默认 `NULL` | 必须由 `user_admin` 在看板审核批准后才可转为 `active`。 |

> **人工操作默认保护**：凡由 `user_admin` 在看板手工新建、编辑、恢复或裁定冲突生成的记忆，服务端默认设置 `locked = 1`（用户可在看板随时手动解锁），确保人工拍板内容天然免疫任何 AI 自动修改。

   * 当 `memory_cli.py` 发起请求时：
     * **Antigravity 通道**：由客户端传入当前 `session_id`（请求头 `X-Session-Id`），网关直接在服务端本机读取 `E:\Harness运行区\Antigravity\state\sessions\<session_id>\context.json`（核验文件存在且 `observed_at` 在有效窗口内），取其 `workspace_paths` 经 `os.path.realpath` 规范化后对照 `project_registry` 解析出 `bound_project_id`；
     * **Codex 通道（或通用 CLI）**：由 `memory_cli.py` 默认自动采集当前进程 `Path.cwd().resolve()` 通过请求头 `X-Workspace-Path` 传给网关，网关校验该目录在磁盘真实存在且匹配 `project_registry` 中的已登记目录，解析出 `bound_project_id`。
   * **防误串强校验规则**：
     * 若当前无工作区（如 `workspace_paths == []`）或上报路径未在 `project_registry` 登记，则服务端判定 **`bound_project_id = NULL`**；
     * 当 `bound_project_id = NULL` 时，`agent_client` **仅允许检索 `scope = 'user_global'` 与该客户端自身的 `scope = 'agent_private'`**，任何针对 `scope = 'project'` 的检索或写入请求一律返回 `403 ProjectScopeMismatch`；
     * 当 `bound_project_id = 'proj_A'` 时，若请求体填写 `"project_id": "proj_B"`，服务端直接拒绝并返回 `403 ProjectScopeMismatch`。
   * **工作区路径可伪造性的诚实边界声明（不夸大安全保证）**：
     * 在同一 Windows 用户账号（`ZhuanZ`）下，本地 HTTP 请求头 `X-Workspace-Path` 或 `X-Session-Id` 属于**协作式客户端防误串工程护栏（旨在防止合规调用的 `memory_cli.py` 误填 `project_id`、无工作区闲聊污染项目库、或 FTS5 跨项目误召回）**；
     * 如果某个拥有本机 Shell 权限的进程故意绕过 `memory_cli.py` 的默认 `cwd` 探测、手工伪造 `X-Workspace-Path: E:/OtherProject` 请求头或枚举磁盘上的其他 `session_id`，单靠本地 HTTP 网关无法从操作系统内核层验证发起进程的真实工作目录。这一点属于已接受的个人单机同账号部署限制，不在首版宣称为防恶意进程欺骗的密码学边界。
2. **AI 申请新建 `user_global` 或跨范围共享的硬拦截**：
   * 若 `agent_client` 请求创建 `scope = "user_global"`（如在无工作区聊天中提炼出的个人跨项目通用偏好），网关**将该记录初始置为 `state = 'paused'`，并自动在 `conflict_proposals` 中生成一条 `proposal_type = 'scope_expansion'` 待确认项**，待用户在看板一键点击“批准启用”后转为 `state = 'active'` 并置 `locked = 1`。

## 3. 优先级准则、凭证分置认证与冲突/Undo 状态机（修订 P0-1, P1-7, P1-9）

### 3.1 四维正交优先级准则

1. **安全、隐私、权限与平台硬边界（最高不可逾越）**：平台安全规则、路径白名单、禁读凭据（`.env`/Token/Cookie）与用户有效授权最先执行，任何当轮口头指令或历史记忆均不可突破。
2. **客观事实与执行进度真相（证据准则）**：以真实运行环境、磁盘产物哈希与控制器收据为准，口头指令与历史记忆均不能把“未完成/未验证”变成“已完成/已验证”。
3. **合法边界内的工作偏好与约定**：遵循 `当前用户明确指令 > 项目现行配置/约定 > 记忆中心历史记录`（即使某条偏好在库内 `locked=1`，用户在当前会话的新指令仍可指导当次任务）。
4. **记忆适用性与权限非扩张原则**：仅满足 `state = 'active' AND confidence = 'confirmed' AND (expires_at IS NULL OR expires_at > now)` 的记录作为默认有效事实返回；记忆绝不授予新行动权限。

### 3.2 客户端 Token 与管理员口令哈希物理分置及隔离边界声明（修订 P1-9）

1. **客户端凭证与管理员认证物理分置（消除“同文件顺手读走管理员 Token”风险）**：
   * **客户端通道凭证文件（`E:/AI运行区/SharedMemoryHub/config/client_tokens.json`，不入 Git）**：
     * 仅存放两个受限 `agent_client` 的随机密钥：`AGY_CLIENT_TOKEN`（绑定 `actor_role="agent_client", actor_id="antigravity"`）与 `CODEX_CLIENT_TOKEN`（绑定 `actor_role="agent_client", actor_id="codex"`）。
     * **该文件中绝不包含任何管理员密钥或口令**。
   * **管理员认证哈希文件（`E:/AI运行区/SharedMemoryHub/config/admin_auth.json`，不入 Git）**：
     * **磁盘上绝不保存明文 `USER_ADMIN_TOKEN` 或明文管理员口令**！
     * 初始化或运行 `scripts/reset_admin_passcode.ps1` 时，由用户在终端交互式输入管理员口令（或由脚本在终端屏幕一次性显示高熵口令且不落盘/不入日志），服务端仅将 `hashlib.scrypt(passcode, salt=..., n=16384, r=8, p=1)` 计算出的 **`salt_hex` 与 `passcode_hash_hex`** 写入 `admin_auth.json`。
     * 因此，即便某个本地 AI 进程读取了 `config/` 下的全部文件，也**无法从磁盘文件中直接获取可用的管理员登录口令或管理员 Bearer Token**。
2. **看板登录与防跨站保护**：
   * 管理看板仅监听 `http://127.0.0.1:8765/ui`；
   * 用户在浏览器打开 `/ui` 输入管理员口令，服务端校验 `scrypt` 哈希通过后，仅在服务端内存维护短期会话（默认 12 小时有效，网关停止即销毁），向浏览器下发 `HttpOnly; SameSite=Strict` 会话 Cookie 及页面内联 `X-CSRF-Token`；所有看板写操作（POST）强制同时校验会话 Cookie、CSRF 令牌与 `Origin: http://127.0.0.1:8765`。
   * 对于命令行管理脚本（如用户在终端手动执行备份/重建），脚本运行时提示用户在控制台交互输入管理员口令，换取单次短期会话令牌，不落盘保存。
3. **同 Windows 账号下的真实安全边界诚实声明**：
   * **可保证的边界**：① 任何通过 HTTP 网关或 `memory_cli.py` 访问的客户端无法伪造 `user_admin` 身份；② 即使 Agent 读取 `config/` 目录也无法获得管理员明文凭证；③ 两端 Harness 规则明令禁止 AI 绕过网关直接读写 `data/sqlite/memory_hub.db` 或 `data/tombstones/`。
   * **不虚假承诺的边界（及首版取舍理由）**：由于网关、SQLite 数据库与两端 AI 均运行在同一 Windows 登录用户（`ZhuanZ`）下，若某个拥有任意 Shell 执行权限的进程完全绕过 HTTP 网关、直接调用底层命令篡改磁盘上的 `.db` 文件，单靠应用层认证无法在操作系统内核层拦截。要阻止同账号 Shell 直改磁盘，必须额外部署独立 Windows 服务账号与 NTFS ACL 权限隔离，但这会显著增加个人单机部署、手动启停与 CUDA 调用复杂度。因此，**首版采用“HTTP 网关强制鉴权 + 管理员口令哈希不落明文 + 审计日志与 Harness 禁直写规则”，不声称已实现操作系统级跨进程强隔离**。

### 3.3 事实冲突与已生效记忆变更提案的四类处置（修订 P0-1）

1. **情况 A：AI 提交同域事实矛盾（`credible_fact_conflict`）**
   * `agent_client` 发现同主题存在矛盾事实，调用 `memory_write(operation='propose_conflict')`；服务端在 `conflict_proposals` 插入提案（`status='pending'`），将 `current_memory.has_open_conflict` 设为 `1`，**但 `current_memory.state` 保持 `'active'` 不变，`revision` 与正文不变**；常规检索照常返回原记录并附带 `conflict_notice`。
2. **情况 B：AI 请求修改或删除跨会话/人工确认的已生效记忆（`update_proposal` / `delete_proposal`，新增）**
   * 当 `agent_client` 对一条非 `handoff` 且非“同端同会话未锁定自纠”的已生效记忆发起 `update` 或 `soft_delete` 时，服务端**不直接覆盖或删除原记录**，而是自动将该请求转为 `conflict_proposals` 中的 `update_proposal` 或 `delete_proposal`（返回 `status="queued_as_proposal"`，原记录保持 `state='active'` 且 `has_open_conflict=1`），由用户在看板一键批准或拒绝。
3. **情况 C：AI 试图修改或删除 `locked=1` 锁定项（`locked_override_attempt`）**
   * 服务端直接返回 `409 LockedConflict` 拒绝修改，可选记入 `conflict_proposals(proposal_type='locked_override_attempt')`；原锁定记录保持 `state='active'` 继续有效。
4. **情况 D：AI 申请写入 `user_global`、扩大共享范围或生成规则候选（`scope_expansion` / `rule_candidate`）**
   * 新建的全局候选或规则候选初始置为 `state='paused'` 并在 `conflict_proposals` 中挂起提案，待用户在看板一键确认后转为 `state='active', locked=1`。

### 3.4 状态转换总表（严格区分 `undo` 撤销上一动作与 `restore` 恢复历史版本，修订 P0-1 & P1-7）

| 动作 (`operation`) | 允许角色 | 前置条件 | 转换后 `state` / `locked` | `revision` 变化 | 向量索引与 FTS5 动作 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **`create`（已绑定项目低风险新增）** | `agent_client`<br>`user_admin` | `expected_revision == 0`，通过准入守卫与来源校准 | `active`（若 `user_admin` 则 `locked=1`） | `0 → 1` | 同步入 `memory_fts`；串行 `upsert` 确定性 point ID |
| **`create`（AI 申建 `user_global` 或 `rule_candidate`）** | `agent_client` | `expected_revision == 0`，通过准入守卫 | **`paused`**（并生 `conflict_proposals`） | `0 → 1` | 暂不入 `memory_fts` 与常规召回，待用户批准转 `active` |
| **`update`（允许直改：人工 / `handoff` / 同会话自纠）** | `user_admin`<br>`agent_client`（仅限允许直改范围且 `locked=0`） | `expected_revision == actual` | 保持原 `state`（若 `user_admin` 则 `locked=1`） | `r → r + 1` | 若 `state=='active'` 更新 `memory_fts` 并串行 `upsert` 同一点 |
| **`update` / `soft_delete`（AI 触碰既有已生效记忆）** | `agent_client` | 非同会话自纠且非 `handoff`，`locked=0` | **保持原 `state`（`active`）不变**（设 `has_open_conflict=1`） | **不变**（转为 `update_proposal` / `delete_proposal`） | 原记录索引保持不变，检索附带 `conflict_notice` |
| **`propose_conflict`（提交事实矛盾）** | `agent_client` | 目标记录存在 | **保持原 `state`（`active`）不变**（设 `has_open_conflict=1`） | **不变**（写入 `conflict_proposals`） | 保持原向量点可搜（回查时附 `conflict_notice`） |
| **`touch_locked`（AI 触碰锁定项）** | `agent_client` | 目标记录 `locked == 1` | **保持原 `state` 与 `locked=1` 不变** | **不变**（返回 `409`） | 无变化 |
| **`lock` / `unlock`（锁定切换）** | 仅 `user_admin` | `expected_revision == actual` | 保持原 `state`，`locked` 置 `1` 或 `0` | `r → r + 1`（保存完整快照） | 若 `active` 则更新 Qdrant payload |
| **`pause` / `resume`（人工暂停/启用）** | 仅 `user_admin` | `expected_revision == actual` | `paused` / `active` | `r → r + 1`（保存完整快照） | `pause` 移出 `memory_fts` 并 `delete` point；`resume` 写回 `memory_fts` 并 `upsert` |
| **`resolve_conflict`（人工裁定提案）** | 仅 `user_admin` | `expected_revision == actual` | `active`, `locked=1`（若无剩余挂起提案则 `has_open_conflict=0`） | `r → r + 1`（记录 `resolved_by_revision`） | 同步 `memory_fts` 并串行 `upsert` 裁定后的最新正文 |
| **`soft_delete`（人工删除 / 允许范围内的软删）** | `user_admin`<br>`agent_client`（仅限允许直改范围） | `expected_revision == actual` | **`deleted`**（保留原 `title/content` 快照） | `r → r + 1` | 从 `memory_fts` 移除 + 串行 `delete` Qdrant point |
| **`undo`（撤销上一动作，P1-7 精确状态逆转）** | 仅 `user_admin` | `expected_revision == r_curr` | • 若 `r_curr == 1`：转为 `state='deleted'`；<br>• 若 `r_curr > 1`：**完整恢复 `r_{curr-1}` 的 `(title, content, state, locked, metadata)`**（若 `r_curr` 为 `resolve_conflict` 则同步将对应提案重开为 `pending`） | `r_curr → r_curr + 1`（`operation='undo'`, `restored_from = r_curr - 1`） | 若恢复后 `state=='active'` 则写入 `memory_fts` 并 `upsert` point；若恢复后为 `paused/deleted` 则移出 `memory_fts` 并 `delete` point |
| **`restore`（从历史抽屉恢复指定旧版 `r_k` 正文）** | 仅 `user_admin` | `expected_revision == r_curr`, `1 <= k < r_curr` | **`active`, `locked=1`**（恢复 `r_k` 的 `title, content, metadata`） | `r_curr → r_curr + 1`（`operation='restore'`, `restored_from = k`） | 写入 `memory_fts` + 串行 `upsert` 恢复后的正文 |
| **`purge`（受控存储永久清除与防复活登记）** | 仅 `user_admin`（需二次确认码 + `expected_revision`） | 记录存在 | **物理移除业务行 + 登记无正文 `purge_tombstones` 与 `purge_registry.jsonl`** | 删除 `current_memory`、`memory_fts`、`revisions`、`conflict_proposals`；将 `requests.is_purged` 置 `1`（返回 `410`） | 取消未完 `index_work`、删除 Qdrant point、`memory_fts` rebuild + `wal_checkpoint(TRUNCATE)` + `VACUUM` |

## 4. 数据模型（9 张关系表 + FTS5 全文表）、权限过滤、混合检索与重建/清除契约（修订 P0-2, P0-3, P0-4, P1-6, P1-8）

    updated_at TEXT NOT NULL
);
```

### 4.2 强制权限闭环、FTS5 子串/短词混合检索与滞后融合规则（修订 P0-2 & P1-8）

当客户端或看板调用 `memory_search`（以及 `memory_precheck`、`memory_get`）时，严格按以下四步执行：

#### 第 1 步：解析服务端可信上下文与活动世代
1. 从认证头解析 `(actor_role, actor_id, host_id)`；
2. 从 `hub_meta` 读取 `allowed_subject`（默认 `"user:zhuanz"`，合成测试时允许 `"user:synthetic_test"`）、`active_index_generation`（对应 Qdrant 集合 `f"memories_{active_index_generation}"`）以及 `project_registry`；
3. 根据调用方上报并经服务端核验的工作区真实路径导出 `bound_project_id`（无工作区时为 `NULL`；若请求体指定了与 `bound_project_id` 冲突的 `project_id` 或越权 `subject`，立即返回 `403 Forbidden`）。

#### 第 2 步：三路候选召回（Qdrant 向量 + FTS5 三字符子串 / 短词 `LIKE` + 滞后未同步行补充）
1. **向量路（Qdrant）**：用 `Qwen3-Embedding-0.6B` 编码查询语句，在 Qdrant 当前世代集合中按 `subject = bound_subject`、`state = 'active'` 及可见 `scope/project_id` 过滤召回 Top-`(top_k * 2)` 候选 `(memory_id, vector_score)`；
2. **关键词路（SQLite `memory_fts` 三字符子串索引 + 2 字符短词 `LIKE` 回退，修订 P1-8）**：
   * **准确机制说明**：SQLite `memory_fts (tokenize='trigram')` 是**三字符连续子串索引**，并非中文语义分词器。若直接将含空格或特殊字符的整句塞入 `MATCH`，会导致语法错误或要求整句连续匹配而漏召回。
   * **查询子词拆分与转义规则**：
     * 服务端先将 `query_text` 按空白符与标点拆分为子词序列（保留形如 `v0.2.0`、`3.50.4` 的版本号与 `E:/AI运行区/...` 的路径片段），并剔除纯单字虚词；
     * **长度 `>= 3` 的子词（含英文技术词 `FastAPI`、`UUIDv5`、路径片段、版本号及 `>=3` 字中文词）**：将双引号转义为 `""` 后包裹为 `"subterm"`，对于长于 4 字的连续中文短语同时提取滑动 3 字窗口，以 `OR` 组合在 `memory_fts` 中执行 `MATCH` 召回，按命中子词覆盖率与 `bm25(memory_fts)` 归一化为 `keyword_score ∈ [0, 1]`；
     * **长度 `== 2` 的双字中文短词（如 `"幂等"`、`"回滚"`、`"锁定"`、`"看板"`、`"显存"`）**：由于 `< 3` 字符无法命中 `trigram` 索引，服务端自动对这些 2 字短词在 `current_memory`（叠加第 3 步权限谓词）上执行参数化 `title LIKE :pat OR content LIKE :pat OR topic_key LIKE :pat` 补充召回！
3. **滞后未同步行显式补充（防止旧向量过滤后新内容搜不到，修订 P1-8）**：
   * 在 `current_memory` 中直接查询满足第 3 步权限谓词且 `indexed_revision < revision`（即刚新增或刚修改、Worker 尚未更新完向量）的活跃记录；若其标题、正文或 `topic_key` 命中任一查询子词（含 2 字子词），直接并入候选池。

#### 第 3 步：强制回查 SQLite 权威表与最终权限门禁（核心闭环，修订 P0-2）
**无论候选 `memory_id` 来自 Qdrant、`memory_fts`、`LIKE` 还是单条 `memory_get` / `memory_precheck`，一律强制通过以下 SQLite 权威查询与权限校验，绝不允许任何一路绕过**：

```sql
SELECT * FROM current_memory
WHERE memory_id IN (...)
  AND state = 'active'
  AND confidence = 'confirmed'
  AND (expires_at IS NULL OR expires_at > :now_utc_iso)
  AND subject = :bound_subject
  AND (
    scope = 'user_global'
    OR (scope = 'project' AND :bound_project_id IS NOT NULL AND project_id = :bound_project_id)
    OR (scope = 'agent_private' AND created_by_actor_id = :actor_id
        AND (:bound_project_id IS NULL OR project_id IS NULL OR project_id = :bound_project_id))
  );
```
随后在应用层对返回的每一行强制执行 JSON 集合校验：
1. `actor_id` 必须存在于 `json.loads(row.readers_json)` 中（`user_admin` 除外）；
2. `"any"` 或当前 `host_id` 必须存在于 `json.loads(row.host_constraints_json)` 中；
3. **验证效果**：即使 `memory_fts` 全表子串匹配到了另一个项目（`proj_beta`）、另一个主体或另一个 Agent 的私有记忆，在第 3 步回查 SQLite 时也会被 `WHERE` 子句 100% 拦截剔除！

#### 第 4 步：版本水位校验与归一化混合排序（修订 P1-8）
1. **已同步记录（`indexed_revision == revision`）**：
   * 标记 `index_status = "synced"`；
   * 综合得分 `final_score = 0.65 * vector_score + 0.35 * keyword_score`（若仅单路命中则按单路得分加上双路共现奖励排序）。
2. **滞后/待同步记录（`indexed_revision < revision`）**：
   * 如实标记 `index_status = "lagging"`；
   * **丢弃 Qdrant 中可能存在的旧版本 `vector_score`**（绝不用旧正文的向量分冒充新版）；
   * 若当前进程内 Embedding 模型空闲且本次查询中 `lagging` 候选数 `<= 3` 条，网关可直接对最新正文实时计算一次余弦相似度作为 `live_vector_score` 参与 `0.65 * live_vector_score + 0.35 * keyword_score` 排序；若模型正忙，则直接使用归一化 `keyword_score`（匹配 `topic_key` 或多子词命中时赋予 `[0.70, 0.95]` 区间权重）参与排序，确保刚写入或刚修改的记忆不会因为旧向量被过滤而沉底或丢失！
3. **冲突提示**：若 `has_open_conflict == 1`，在返回项中附加 `conflict_notice` 字段提醒存在待裁定提案。

### 4.3 单串行 Worker 故障恢复、重建写冻结与 Purge 防复活规程（修订 P0-3, P0-4, P1-6）

#### (1) 单串行 Worker 崩溃恢复、任务折叠、超时退避与双检水位机制（修订 P1-6）
1. **单实例进程锁（防多进程/重复启动挤爆显存）**：
   * FastAPI 网关启动时固定单 Worker 进程（`uvicorn --workers 1`），并尝试获取 `E:/AI运行区/SharedMemoryHub/data/hub.lock` 的操作系统排他文件锁（Windows `msvcrt.locking`）；若锁已被占用，立即退出并报错提示已有实例运行，绝不重复加载第二份 `Qwen3-Embedding-0.6B` 模型。
2. **启动恢复（Crash Recovery）**：
   * Worker 协程启动时，首先扫描 `index_work` 中所有 `status = 'processing'` 的中断残留行，将其统一重置为 `status = 'pending', claimed_at = NULL, last_error = 'recovered_after_restart'`。
3. **任务认领与同 ID 自动折叠（Task Claim & Coalescing）**：
   * Worker 按 `status = 'pending' AND (next_retry_at IS NULL OR next_retry_at <= :now)` 顺序认领最早一条任务，置 `status = 'processing', claimed_at = :now`；
   * 若发现同一个 `memory_id` 在队列中还有更高 `target_revision` 的 `pending` 任务，立即将较低 `target_revision` 的任务全部标为 `'superseded'`，直接认领最新 `target_revision`，避免无意义的中间版本编码。
4. **硬超时、有界指数退避公式修正与推理线程底层阻塞保护（Timeout, Bounded Retry & Wedged Thread Guard）**：
   * 单条模型推理设置协程等待超时 `15s`，Qdrant 写入/删除设置 HTTP 超时 `10s`；
   * **精确 3 次重试退避公式（修正 P1-4）**：初始 `retry_count = 0`；每次发生异常或超时先执行 `retry_count += 1`：
     * 当 `retry_count <= 3`（即第 1、2、3 次失败）时：置回 `status = 'pending'`，设置退避时间 `next_retry_at = now + 5 * (3 ** (retry_count - 1))` 秒（精确对应第 1 次重试 `+5s`、第 2 次 `+15s`、第 3 次 `+45s`）；
     * 当 `retry_count > 3`（即初始尝试 + 3 次重试全部失败，第 4 次失败）时：置为 `status = 'failed'`，记录 `last_error`，在看板顶部显示可一键重试的告警横幅。
   * **模型推理超时不能强杀底层 C++/CUDA 线程的诚实处理**：
     * Python `Future.result(timeout=...)` 超时仅解除调用者等待，**无法在操作系统层面强行终止同一进程内正在执行 C++/CUDA 前向计算的底层线程**；
     * 因此，服务端以非阻塞互斥锁 `_embedding_infer_lock` 保护模型推理入口；一旦发生 `15s` 推理超时且锁未释放，网关立即将内部状态标为 `embedding_engine_wedged = True`，暂停后续 Worker 编码任务，并将 `memory_search` 自动降级为纯 SQLite `memory_fts` + `LIKE` 关键词检索模式（跳过实时 Query 向量编码，防止检索请求排队卡死在阻塞的 CUDA 锁上），同时在看板顶部与 `/v1/health` 提示用户执行 `stop_hub.ps1` / `start_hub.ps1` 重启网关进程。
5. **编码前后双阶段水位与墓碑复核（Double Watermark Check）**：
   * **编码前**：检查 `purge_tombstones` 与 `current_memory`；若该 `memory_id` 已 Purge，或 `current_memory.revision != target_revision`，或 `index_generation != generation`，直接将任务置为 `'superseded'`；
   * **编码并写入 Qdrant 后**：在 SQLite 事务中执行带 `WHERE revision = :target_revision AND state = 'active' AND index_generation = :generation` 的条件更新；若 `rowcount == 0`（说明编码耗时期间记录又发生了修改、暂停、软删或 Purge），立即将本任务标为 `'superseded'`，并若当前状态已非 `active` 则立即调用 `qdrant_client.delete` 清理刚刚写入的向量点！

#### (2) 索引世代（`index_generation`）写冻结重建、摘要核验与中断崩溃恢复规程（`admin_reindex`，修订 P0-2/P0-3）
为彻底解决“重建期间并发写入、仅靠数量相等掩盖版本漂移、提前将旧任务标为 `superseded` 导致回退丢任务、以及重建中途进程崩溃遗留 `maintenance_mode` 锁死系统”的问题，采用以下七步规程：
1. **开启重建写冻结并记录目标世代**：在 `hub_meta` 中记录 `maintenance_mode = "reindexing"` 与 `staging_index_generation = target_gen`；重建期间任何 `memory_write` 或看板写操作立即收到 `503 ServiceUnavailable (error_code="reindex_in_progress", retry_after_seconds=15)`；读请求（`memory_search`, `memory_get`）继续无感读取**旧世代集合**。
2. **排空并暂停 Worker（严禁提前作废旧世代 `pending` 任务）**：等待单串行 Worker 完成当前正在处理的 1 条任务（若有）并暂停队列消费；**此时绝不将旧世代剩余 `pending` 任务提前标为 `'superseded'`**，确保若重建失败回退，旧世代未完成任务依然完好待命！
3. **采集权威快照并计算版本清单摘要**：从 SQLite `current_memory` 读取全部 `state = 'active'` 的记录，按 `memory_id` 升序排列计算确定性清单哈希：`expected_manifest_sha256 = sha256("\n".join(f"{r.memory_id}:{r.revision}:{r.updated_at}" for r in active_rows))`。
4. **写入目标集合 `memories_{target_gen}`**：创建或清空 Qdrant 集合 `memories_{target_gen}`，逐批编码全部活跃记录并写入确定性 UUIDv5 点，payload 中显式写入 `memory_id`、`revision`、`updated_at` 与 `generation = target_gen`。
5. **双重一致性核验（数量 + 逐点版本摘要）**：从 `memories_{target_gen}` 遍历拉取全部点的 payload（无需拉取向量），计算 `actual_manifest_sha256 = sha256("\n".join(sorted(f"{p.memory_id}:{p.revision}:{p.updated_at}")))`，并重查 SQLite 确认：`point_count == len(active_rows)` **且** `actual_manifest_sha256 == expected_manifest_sha256`。
6. **原子切换（此时才一并作废旧世代任务）或失败回退**：
   * **核验通过**：在**同一笔 SQLite 事务**中，更新 `hub_meta.active_index_generation = target_gen`、将所有活跃记录更新为 `index_generation = target_gen, indexed_revision = revision`、**此时才将 `index_work` 中旧世代残留的 `pending/processing` 任务统一置为 `'superseded'`**、并将 `hub_meta.maintenance_mode` 恢复为 `"normal"`（清除 `staging_index_generation`），随后唤醒 Worker 并安全删除旧 Qdrant 集合。
   * **核验失败或中途异常回退**：保持 `hub_meta.active_index_generation` 指向**旧集合**不变，删除半成品 `memories_{target_gen}`，恢复 `maintenance_mode = "normal"`，并将旧世代因中断残留的 `processing` 任务重置为 `pending`，唤醒 Worker 继续消费旧世代队列。
7. **重建中途进程崩溃与重启自动恢复（Startup Reindex Recovery）**：
   * 网关每次启动时检查 `hub_meta.maintenance_mode`：若发现遗留 `"reindexing"`，说明上次重建中途发生进程崩溃，而 `active_index_generation` 仍安全停留在旧世代；
   * 启动恢复程序自动执行：① 将 `hub_meta.maintenance_mode` 重置为 `"normal"`；② 若存在 `staging_index_generation` 半成品 Qdrant 集合则予以清理；③ 扫描 `current_memory` 中所有 `state = 'active' AND (indexed_revision < revision OR index_generation != active_index_generation)` 的记录，若其在 `index_work` 中无对应的 `pending` 任务则自动补齐插入一条 `action='upsert', status='pending'` 任务，确保无论何时崩溃重启均不会遗漏任何一条待索引记录！

#### (3) 受控存储清除（Purge）跨存储一致性、先写哈希链墓碑与缺证据拒绝上线规程（修订 P0-3/P1-5）
1. **消除 SQLite 与外部墓碑文件之间的崩溃窗口（Write-Ahead Tombstone 顺序）**：
   * 在 `E:/AI运行区/SharedMemoryHub/data/tombstones/purge_registry.jsonl` 初始化时写入创世头记录（`seq = 0`, `entry_hash = sha256("genesis")`），并在 `hub_meta`（及每次备份的元数据清单）中同步记录当前最大墓碑序号 `max_purge_seq`。
   * 当执行 `Purge`（对回收站记录，或对活跃记录传入 `confirm_purge="PURGE <memory_id> r<expected_revision>"` 及 `expected_revision`）时，严格按以下 **先写外部持久墓碑 → 再删 SQLite → 启动/恢复强制对账** 顺序执行：
   * ① **第 1 步（先追加并 `fsync` 独立外部哈希链墓碑，消除崩溃复活窗口）**：
     * 计算被清除正文的不可逆哈希 `purged_content_sha256 = sha256(f"{title}\n{content}")`，分配 `seq = max_purge_seq + 1`，计算链式哈希 `entry_hash = sha256(f"{prev_hash}:{seq}:{memory_id}:{purged_content_sha256}")`；
     * 先将无正文记录 `{"seq": seq, "prev_hash": prev_hash, "entry_hash": entry_hash, "memory_id": memory_id, "request_keys": [...], "purged_content_sha256": ..., "purged_at": ..., "actor_id": ...}` 追加写入 `data/tombstones/purge_registry.jsonl` 并调用 `os.fsync()` 强制落盘（若此步写盘失败则直接中止返回错误，SQLite 未发生任何部分修改）。
   * ② **第 2 步（SQLite 单事务抹除业务行并锁定幂等键）**：
     * 删除 `current_memory`、`memory_fts`（已开启 `secure-delete=1`）、`revisions`、`conflict_proposals` 四张表中属于该 `memory_id` 的全部行；
     * 执行 `UPDATE requests SET is_purged = 1, status_code = 410 WHERE memory_id = :memory_id`（保留无正文幂等键，阻止旧请求重放重建）；
     * 将该 `memory_id` 所有未完成 `index_work` 标为 `'superseded'`；
     * 在 `purge_tombstones` 表插入 `(memory_id, purge_seq, entry_hash, purged_content_sha256, purged_at, actor_id)`，更新 `hub_meta.max_purge_seq = seq`，并在 `audit_events` 写入无正文墓碑事件。
   * ③ **第 3 步（FTS5 影子表重构、WAL 截断与数据库重整）**：
     * 显式执行 `INSERT INTO memory_fts(memory_fts) VALUES('rebuild');`，紧接着执行 `PRAGMA wal_checkpoint(TRUNCATE);` 与 `VACUUM;`（配合 `PRAGMA secure_delete=ON` 与 FTS5 `secure-delete=1` 双重保障）。
   * ④ **第 4 步（Qdrant 向量点与受控导出清理）**：从所有 Qdrant 集合删除该 `memory_id` 对应的确定性 UUIDv5 点，并清理/重生 `exports/` 下的受控导出文件。
2. **启动对账与历史备份恢复的“缺墓碑证据拒绝上线（Fail-Closed）”强制门禁**：
   * **崩溃自动补齐（Crash Reconciliation）**：若进程在第 ① 步 `purge_registry.jsonl` 落盘后、第 ②/③/④ 步完成前崩溃，网关在下一次启动（以及每次执行 `admin_backup_restore`）时，在开放 HTTP 端口前强制运行 `reconcile_purge_registry()`：遍历 `purge_registry.jsonl` 中所有 `memory_id`，凡在 SQLite 业务表或 Qdrant 中仍有残留的，自动补跑第 ②、③、④ 步彻底清除并更新 `max_purge_seq`！
   * **恢复证据缺失或损坏时强制拒绝上线（Fail-Closed）**：
     * 在网关启动或执行 `admin_backup_restore` 恢复任何历史备份时，必须首先校验 `data/tombstones/purge_registry.jsonl`：
       1. 文件必须存在且可读；
       2. 从 `seq = 0` 到末尾的每一行 JSON 与 `prev_hash -> entry_hash` 哈希链必须 100% 校验通过；
       3. 文件末尾的最大序号 `file_max_seq` 必须 `>= max(当前库 max_purge_seq, 待恢复备份记录的 max_purge_seq)`。
     * **一旦上述任一条件不满足（例如 `purge_registry.jsonl` 被误删、截断或哈希链校验失败），备份恢复程序或网关启动立即中止并拒绝上线（返回 `503 / restore_aborted: missing_or_corrupted_purge_evidence`）**，严禁在缺失删除墓碑证据的情况下将旧备份切换上线！
2. **诚实的清除边界与 `purge_receipt` 结构（不以数据库清理推断全盘物理零残留）**：
   * `purge_receipt` 明确区分“已实测清零的受控活动存储”与“未承诺或可选清理范围”：
   ```json
   {
     "status": "purge_pending",
     "memory_id": "mem_example",
     "purge_receipt": {
       "memory_id": "mem_example",
       "purge_seq": 1,
       "entry_hash": "<hash>",
       "purged_content_sha256": "<hash>",
       "purged_at": "<UTC>",
       "actor_id": "user",
       "sqlite_done": 1,
       "vector_done": 0,
       "exports_done": 1,
       "compact_done": 1
     },
     "scope_notice": "受控活动 SQLite、向量世代与 active_memories 导出；历史备份恢复须重放墓碑，不承诺宿主日志与物理磁盘块。"
   }
   ```

## 5. 单页管理看板、精确 Undo/Restore 与两端真实调用闭环（修订 P0-5 & P1-7）

### 5.1 单页管理看板（`http://127.0.0.1:8765/ui`）核心交互与 Undo / Restore 语义分离

* **状态声明**：单页看板与版本面板已实现；浏览器实测结果单独记入本版回执。
* **严格区分“撤销上一动作（Undo）”与“恢复指定版本正文（Restore）”（修订 P1-7）**：
  1. **撤销上一动作（`POST /v1/admin/memory/{memory_id}/undo`，看板顶部横幅与操作回退按钮）**：
     * **语义目标**：精确逆转最近一次修订 `r_{curr-1} → r_curr` 所造成的**全部状态与内容变化**，绝不把“撤销锁定/暂停/删除”误做成“仅覆盖正文且强行设为 `active`”。
     * **执行规则（携带 `expected_revision = r_curr`）**：
       * 若 `r_curr == 1`（上一动作是新建 `create`）：生成 `r_2 (operation='undo', restored_from=0)`，将 `state` 置为 `'deleted'`（保留 `title/content` 快照供回收站查看），从 `memory_fts` 与 Qdrant 移除；
       * 若 `r_curr > 1`（上一动作可能是 `update`、`lock`、`unlock`、`pause`、`resume`、`soft_delete`、`restore` 或 `resolve_conflict`）：从 `revisions` 读取 `r_{curr-1}` 的完整快照，生成 `r_{curr+1} (operation='undo', restored_from=r_{curr-1})`，**完整还原 `r_{curr-1}` 的 `title`、`content`、`state`、`locked` 与 `metadata_snapshot_json`**！
         * 例 1：上一动作是 `lock`（`r1: active, locked=0` → `r2: active, locked=1`），点击 Undo 后生成 `r3: active, locked=0`（准确解除锁定）；
         * 例 2：上一动作是 `resume`（`r1: paused` → `r2: active`），点击 Undo 后生成 `r3: paused`（准确退回暂停态并从检索移除）；
         * 例 3：上一动作是 `soft_delete`（`r1: active` → `r2: deleted`），点击 Undo 后生成 `r3: active`（准确从回收站恢复并重新入索）；
         * 例 4：上一动作是 `resolve_conflict`，点击 Undo 后除还原 `r_{curr-1}` 快照外，同步将关联的 `conflict_proposals` 重新置为 `status='pending'` 且 `has_open_conflict=1`。
  2. **恢复指定历史版本正文（`POST /v1/admin/memory/{memory_id}/restore`，右侧修订历史抽屉）**：
     * **语义目标**：当用户在历史版本列表 `r_1 .. r_curr` 中挑中任意旧版 `r_k` 并点击“恢复此版正文”时，将 `r_k` 的 `title`、`content` 与 `metadata_snapshot_json` 恢复为当前最新生效内容（生成 `r_{curr+1}`, `operation='restore'`, `restored_from=k`, `state='active'`, `locked=1`）。
  3. **并发安全（CAS）**：`undo` 与 `restore` 均强制校验 `expected_revision == actual_revision`，不匹配时返回 `409 RevisionConflict`。

### 6.4 异常立即停止条件（Stop Criteria）

实施与测试期间若出现以下任一情况，立即停止推进并保留现场报告：
1. 任何进程在受控目录 `E:/AI运行区/SharedMemoryHub/` 之外创建应用级缓存/配置（如创建 `C:\Users\ZhuanZ\.mem0` 或写入 C 盘 HuggingFace 模型缓存），或发起未授权外部网络请求；

4. 本地 `Qwen3-Embedding-0.6B` 在 RTX 2060 (6GB) 上出现显存溢出或单实例锁失效。
